# 可行性與原作還原對照

## 結論

Order To Cook 的訂單、菜單、等級、餐盤及設備狀態均能以 Bedrock 行為包、資源包及穩定 Script API 重寫。原作已有 GeckoLib／Blockbench 格式資源，因此能保留大量原模型、UV、紋理及聲音；跨平台主要成本在程式、介面與動畫驅動。

本文件對應 **0.1.1-alpha.2**。此版在經營主流程上，接上餐盤逐段進食、持續髒盤與提前收盤、七個原作顧客動作，以及獨立冰箱門和洗碗機關鍵姿態。**完整一比一仍未達成**：Java 的 GUI、GeckoLib renderer、玩家動畫、物理與跨模組 API 仍有適配差異，真實客戶端畫面、表單、觸控與多人操作也尚未完成驗收。

基準：[官方作品頁](https://www.curseforge.com/minecraft/mc-mods/order-to-cook)，Java [e59e3dbcabe19b783d9adb933db5fcb8bc1e4642](https://github.com/breezeth-CN/OrdertoCook/tree/e59e3dbcabe19b783d9adb933db5fcb8bc1e4642)。證據分層：源碼對照、單元／服務回歸、原生伺服器探針、客戶端驗收。前三者不能代替最後一層。

## 互通與資料

| 原作能力 | Bedrock 路線 |
| --- | --- |
| 食物自動識別 | 固定40種原版表＋自訂food component；元資料不可讀的食品由管理員註冊。需要逐個實際附加包驗證。 |
| Java mod cooking integration | 不能直接共用Forge/Fabric registry；首版爐灶有可擴充表，但沒有自動移植農夫樂事／森羅等配方。 |
| 自訂貨幣 | 可指定一個已安裝的物品作貨幣，每件一單位。沒有直接呼叫SDM數位帳本。 |
| Jade顯示 | 由設備互動訊息／表單提供計數與進度；不是Jade原介面。 |
| 女僕、航空學等API | 沒有直接移植。需要對相應基岩附加包建立各自的協議。 |
| 多人資料 | 餐廳與設備用固定UUID下的分片world dynamic properties；實物用原生inventory。兩buffer最後提交manifest。 |
| 跨版本／重啟 | 門姿態、廚電剩餘 tick、餐點生命週期與顧客完成時間各自恢復；各版已執行的驗證以 [VALIDATION.md](VALIDATION.md) 為準。真實客戶端卸載／重載、手機和多人併發仍待驗收。 |

存檔分片保證單筆記錄切換完整快照；**世界磁碟、玩家背包和實體庫存並不是可跨服務提交的同一筆資料庫交易**。目前同步操作預檢及回退能防止常見競態／扣物失敗，不能把它描述成任何強制斷電時刻都絕不丟失物品的保證。

領髒盤先保存不可重複領取的 claim，再寫入玩家背包。已知的同步寫入例外會回退；若程序恰在 durable claim 與物品寫入之間終止，可能損失該一個盤子。提前收盤的 0.5 秒中斷時序另存於不可再發盤的待清理記錄，避免歷史裁剪或重啟把顧客恢復成舊進食動作。拆機時若舊盤位置未載入，餐廳維持移除中，暫停新營業與交易，待原錨點清理完畢。

## 直接生成與動作的源碼依據

固定提交的 [OrderNpcManager.java](https://github.com/breezeth-CN/OrdertoCook/blob/e59e3dbcabe19b783d9adb933db5fcb8bc1e4642/forge-1.20.1/src/main/java/cn/breezeth/ordertocook/core/OrderNpcManager.java) 在 `spawnPreparedNpc` 直接定位並掛上座位；`findSpawnPosNormal` 無椅時呼叫 5 格範圍的 fallback。[WalkInNpcManager.java](https://github.com/breezeth-CN/OrdertoCook/blob/e59e3dbcabe19b783d9adb933db5fcb8bc1e4642/forge-1.20.1/src/main/java/cn/breezeth/ordertocook/core/WalkInNpcManager.java) 無空椅即停止生成。[CustomerEntity.java](https://github.com/breezeth-CN/OrdertoCook/blob/e59e3dbcabe19b783d9adb933db5fcb8bc1e4642/forge-1.20.1/src/main/java/cn/breezeth/ordertocook/entity/CustomerEntity.java) 設 movement speed 0、只加入看向玩家／隨機看向目標，並分開管理 idle 變體及特殊 action。完整數值與餐盤依據見 [UPSTREAM_RULES.md](UPSTREAM_RULES.md)。

站立堂食顧客約 3 秒完成 action 4 離場，盤子仍獨立到第 5 秒變髒；這來自原作的放盤、完成動畫及餐盤 tick 三個獨立流程，並非移植新增的提前離場。原呼叫鏈與具體函式同樣記於 [UPSTREAM_RULES.md](UPSTREAM_RULES.md#十顧客餐盤與動畫的來源契約)。

## 後續驗收優先順序

1. 真客戶端跑完整生存循環，以及兩名玩家同時接單／打包／取貨／交付。
2. 對照Java固定視角核對所有家具方向、UV、盤面與顧客姿勢。
3. 調校載具碰撞與輸入、完成手機／控制器操作及跨區塊重啟測試。
4. 比對新餐盤階段、7 個顧客 action 和有限取樣廚電動畫，記錄與原作 easing、放盤片段及畫面時序的差異，再逐項建立其他基岩料理／貨幣包的聯動。

這些項目均列在 [PLAYTEST.md](PLAYTEST.md)，不能因為alpha通過腳本測試就標成已完成。
