# 可行性與原作還原對照

## 結論

Order To Cook 的訂單、菜單、等級、餐盤及設備狀態均能以 Bedrock 行為包、資源包及穩定 Script API 重寫。原作已有 GeckoLib／Blockbench 格式資源，因此能保留大量原模型、UV、紋理及聲音；跨平台主要成本在程式、介面與動畫驅動。

本專案第一個 alpha 已打通經營主流程，也實作了顧客、機車和進階廚電。**完整一比一仍未達成**，尤其不能把 Java 的 GUI、GeckoLib renderer、玩家動畫、物理與跨模組 API 原封不動放進 Bedrock。

基準：[官方作品頁](https://www.curseforge.com/minecraft/mc-mods/order-to-cook)，Java [e59e3dbcabe19b783d9adb933db5fcb8bc1e4642](https://github.com/breezeth-CN/OrdertoCook/tree/e59e3dbcabe19b783d9adb933db5fcb8bc1e4642)。證據分層：源碼對照、單元／服務回歸、原生伺服器探針、客戶端驗收。前三者不能代替最後一層。

## 核心玩法

| 原作特性 | 首版状态 | 實作與差異 |
| --- | --- | --- |
| 立牌決定菜單 | 已實作 | 每牌最多150種；不耗材範本、按每道一份營養；在允許的附近牌中取最高營養單牌。 |
| 五階候選單 | 已實作 | 原權重50/25/15/8/2、菜種數與每種數量範圍、等級加成。不同平台亂數序列不逐位相同。 |
| 接單互斥 | 已實作 | 接打單機的一張後取消同輪其他普通候選，到店單獨立。 |
| 普通、加急、外送、遠距 | 已實作 | 30/10分鐘、30%基礎配送、配送中10%遠距、50–450與1500–3000格等來源常數。 |
| 到店顧客 | 已實作 | 按原等級機率判定；offered就有可點顧客。座位安排代替完整走入流程。 |
| 訂單物品／包裹／餐盤 | 已實作 | 真ItemStack附餐廳、訂單和proof；存入載具保留元資料；核心狀態防重複結算。 |
| 操作台取料 | 已實作並適配 | 取玩家背包與可使用的附近冰箱；不照搬原12格GUI。先核對整筆需求再扣物。 |
| 真實擺放成品 | 已實作 | 在操作台上方生成原盤／袋模型；點取、蹲下擺放、破壞掉回有效成品。 |
| 菜品模型的逐口變化 | 資源已轉換，玩法未完整驅動 | 10種×4階段已轉換，初次裝盤會選擇完整盤型；尚未在每次顧客咀嚼時遞進所有盤面。 |
| 盤子與洗碗循環 | 已實作並適配 | 用餐後髒盤掉落、清洗、補架；洗碗改按一下並保持空手／視線4秒。 |
| 8級餐廳 | 已實作 | Lv0起步、原成本／營養門檻；營養下降使收益福利降階，不退款已買等級。 |
| 金幣、小費及排行 | 已實作 | 1/5/20/100/10000面額、原子找零、多維統計；雨天由穩定weatherChange事件追蹤。 |
| 特殊彩蛋顧客及完整獎勵 | 未移植 | 計算核心保留額外小費參數，首版不生成原Java特殊人物／好吃到爆炸流程。 |
| 遊戲成就 | 未移植 | 沒有重造Java advancement系統或全部隱藏成就。 |

## 設備、畫面及操作

| 項目 | 保留內容 | 已知差異／待驗收 |
| --- | --- | --- |
| 打單機／立牌／桌椅／架子 | 原模型紋理、朝向、容量可見狀態、音效 | 客戶端的模型方向、UV與破壞粒子須實機確認；表單取代Java視窗。 |
| 冰箱 | 真正兩格、27＋54格、真實物品保存、門姿勢 | 每疊上限按Bedrock物品本身；雙門同步，沒有完整平滑動畫及內部食品陳列。 |
| 洗碗機 | 16盤容量、原phase與時間、抽屜姿態 | 相位切換，原逐幀GeckoLib彈跳／開關動畫尚未全接線。 |
| 三槽爐灶 | 3輸入＋1燃料＋3輸出、共用燃燒、火焰煙霧 | 9條明確配方，非通用Java配方registry；其他料理附加包需新增對應。 |
| 顧客 | 兩款原皮膚／骨架、等待／坐姿／進食片段 | 直接就座、無完整進門尋路；不下載網路玩家皮膚。 |
| 椅子／玩家動作 | 玩家可坐、顧客原姿勢 | 沒有玩家洗碗、喝彩、專用騎車等完整動作；未覆寫player.json。 |
| 小電驢 | 原Java模型、四車色、保溫箱、燈面、喇叭 | 原生載具物理及按鍵；燈面發光但不照亮地形。玩家頭盔自动装備／姿勢未全面重現。 |
| 原始美術 | 67原PNG、12原OGG原樣保留；原geo／動畫正規化存档 | 保存未使用片段不等於其在玩法中已被觸發；動畫清單詳見ASSET_PROVENANCE。 |

## 互通與資料

| 原作能力 | Bedrock 路線 |
| --- | --- |
| 食物自動識別 | 固定40種原版表＋自訂food component；元資料不可讀的食品由管理員註冊。需要逐個實際附加包驗證。 |
| Java mod cooking integration | 不能直接共用Forge/Fabric registry；首版爐灶有可擴充表，但沒有自動移植農夫樂事／森羅等配方。 |
| 自訂貨幣 | 可指定一個已安裝的物品作貨幣，每件一單位。沒有直接呼叫SDM數位帳本。 |
| Jade顯示 | 由設備互動訊息／表單提供計數與進度；不是Jade原介面。 |
| 女僕、航空學等API | 沒有直接移植。需要對相應基岩附加包建立各自的協議。 |
| 多人資料 | 餐廳與設備用固定UUID下的分片world dynamic properties；實物用原生inventory。兩buffer最後提交manifest。 |
| 跨版本／重啟 | 已有BDS重啟探針與純邏輯重載測試；仍需客戶端區塊卸載、手機、伺服器併發驗收。 |

存檔分片保證單筆記錄切換完整快照；**世界磁碟、玩家背包和實體庫存並不是可跨服務提交的同一筆資料庫交易**。目前同步操作預檢及回退能防止常見競態／扣物失敗，不能把它描述成任何強制斷電時刻都絕不丟失物品的保證。

## 後續驗收優先順序

1. 真客戶端跑完整生存循環，以及兩名玩家同時接單／打包／取貨／交付。
2. 對照Java固定視角核對所有家具方向、UV、盘面與顧客姿勢。
3. 調校載具碰撞與輸入、完成手機／控制器操作及跨區塊重啟測試。
4. 補盤面逐口變化、平滑廚電動畫、入店尋路，再逐項建立其他基岩料理／貨幣包的聯動。

這些項目均列在 [PLAYTEST.md](PLAYTEST.md)，不能因為alpha通過腳本測試就標成已完成。
