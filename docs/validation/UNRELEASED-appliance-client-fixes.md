舊轉換器把開門姿態推回恰好 30 像素範圍，接著把座標序列化至小數六位。
重新讀取輸出後，`lower_7` 的最小 Z 是 `-22.0000003200404`，`upper_6` 是
`-22.000000379602668`。兩者皆略超過原生日誌邊界；舊測試的 `0.00001` 容差將其放行。
這能重現數值缺陷，不等於宣稱已重跑原生渲染器。

`bound_fridge_swing` 現保留 `1/1024` 像素的向內餘量，再經原有的六位序列化。
修正後兩者最小 Z 分別為 `-21.999023320040397`、`-21.99902337960267`。

相對上游姿態的總修正仍少於 0.125 像素；關閉／全開端點及櫃體不變。
重新執行完整轉換器只改變這兩個 geometry，來源素材與來源 ledger 均不變。

`assert_block_bounds` 同時檢查 30 像素總跨度和實機日誌給出的包圍範圍。
日誌的方塊座標 `[-0.875,1.875]` 換成模型座標是 X/Z `[-22,22]`、Y `[-14,30]`。
不再用放寬容差把越界姿態判成有效。

## 水花：補齊原生粒子的輸入

原本手洗與洗碗機直接呼叫 `minecraft:water_splash_particle`，沒有提供方向變數。
[Mojang 的粒子定義](https://github.com/Mojang/bedrock-samples/blob/main/resource_pack/particles/water_splash.json)
使用 `variable.direction.x/y/z`，與實機 `.x/.y/.z` 錯誤相符。

兩條玩法路徑改用同一個 `safeWaterSplash`，在每次發射時建立獨立 `MolangVariableMap`，
呼叫 `setVector3('variable.direction', {x:0,y:-1,z:0})`。
原生粒子的初速為 -6，因此該方向給出向上的水花初速。
不改原發射位置、20 tick 回饋節奏、音效、洗碗時間、盤數、權限或取消規則。
不換成需要引擎手動發射的 `_manual` 粒子，不增加另一套資源包。
粒子 API 拋例外時只略過該次視覺效果，洗碗及盤子計帳仍繼續。
