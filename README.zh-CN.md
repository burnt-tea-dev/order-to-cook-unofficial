**简体中文** · [繁體中文](README.md) · [English](README.en.md)

## 生存模式开店步骤

1. **建立餐厅。** 合成并放置打单机、菜单立牌、操作台、包装架、餐盘架、椅子和洗碗池。不同餐厅的打单机相距须超过 24 格。
2. **设置菜单。** 用食品点击立牌加入菜式，不消耗食品。空手／潜行点击可管理菜单。每道菜只计算一份营养，不按手上堆叠数累加。
3. **补货。** 用皮革补包装架、干净餐盘补餐盘架。两架必须在操作台 **5 格内**；操作台、椅子与相关冰箱必须在餐厅附近 **24 格内**。
4. **营业和接单。** 点击打单机开启营业并选择一张候选单。接下一单后，同批其他候选会消失；到店顾客的独立订单不受影响。
5. **准备成品食物。** 将订单要求的食物放在背包或可使用的附近冰箱。手持有效订单点击操作台可直接装盘／打包；空手点击可在同一页查看菜名、数量和缺料。**操作台不会自动制作整道料理**，它消耗已经做好的食品。
6. **交付。** 操作台上方须留空，成品盘／包裹会出现于台面。点击拿起，在手持时点击对应顾客交餐。蹲下摆放再取回会[保留完整成品资料](docs/PARITY.md#未交付的展示餐點)。外送包裹和订单可显示目的地与方向。
7. **收款、收盘与清洗。** 完成订单领取 oTc 币和可能的小费。堂食约 5 秒吃完，脏盘留在桌前；店主或员工点击盘子／桌面收取，放进洗碗池，空手点击并连续看向池子 **4 秒**。将干净盘补回餐盘架。同一桌的旧盘必须先收走才能交下一餐。
8. **扩建。** 用金币升级餐厅，在打单机购买设备。工具箱可将两格高的空木桶升级为冰箱、空烟熏炉升级为三槽炉灶、无餐盘洗碗池升级为洗碗机。

普通单 **30 分钟**、加急单 **10 分钟**，从生成时开始倒计时。打单机默认累计 **10 分钟营业运作时间**刷新，暂停／区域停止运作／关服时停计并保存余时；餐厅最高 **8 级**。订单期限按世界总 tick 计算，关服不倒数；服务器运行时离开区域仍会到期。厨房电器所在区域未加载时不补算烹饪进度。

> 默认立牌只有四道菜；40 种原版食品总营养为 159，只靠原版表最多升至 Lv.3。尚未发布的源码加入 67 种正营养森罗食品及 72 种零营养饮品，完整目录营养合计 490，可支持 Lv.7，仍不足原版 Lv.8 的 600。喜糖活动已结束，排除后为 470；其他获取限制见[食品目录](docs/FOOD-CATALOG.md)。饮品不增加营养，升级门槛保持原值。

## 明确改编和未完成项

- 冰箱使用真实原生容器；炉灶和操作台采用直接操作及单页表单，没有完全相同的 Java 专用槽位布局和快捷键。
- 蹲下空手点击冰箱上／下层可整理当前那层：同数据合并，按原先出现顺序收拢；保留名称和 metadata。原生堆叠上限不变，仍无食品限定和每格 128 件。
- 洗碗机持脏盘准星预览已接线，由合资格玩家共用方块姿态；Java 是每客户端独立预览。外卖袋放置动画在卸载时暂停，打单机重启后恢复待取纸张；实机播放节奏仍待比较。
- 立牌／打单机的掉落物已带菜单及原店主／等级／统计等持久资料；Bedrock 记录仍按放置坐标识别，不等于 Java 数字机器 ID。见 [原生资料证据](docs/validation/0.1.10-alpha.1/PORTABLE_NATIVE.md)。
- 26.60 没有可用的原生容器强制关闭 API：撤权后不能保证立即终止已打开的冰箱界面。新开入口的 before-event 取消是否能拦截原生窗口仍待真 Player 验收；不能将当前冰箱当作已验证的私人保险箱。详见 [权限边界](docs/NATIVE-CONTAINERS.md)。
- 源码核对确认原版顾客也是直接生成，并非从门口寻路。普通堂食优先使用 24 格内座椅，无椅则在 5 格内站立；到店顾客必须有座椅。七位彩蛋人物的姓名、身份、小费与反应已接线；线上玩家皮肤下载及女仆联动尚未完成。
- 普通坐席顾客有原版 10% 惊喜反应和 `1–4＋餐厅等级` 加赏。加赏在约6秒动画结束后支付；提前收盘会打断原生查询顺序中的第一位附近进食者，取消该人的待付加赏，可能影响另一桌。第5秒后取脏盘及打破餐盘不取消。离线者不补发个人币，餐厅仍计入加赏。同位置旧盘须先收走，而 Java 会替换并掉落旧盘。
- 手洗FP已补臂长及肩端补位；安坐／拍手接原全身、前臂与足端，拍手分TP／FP且保持原持物玩法。空手左臂须接共享多request设置，独立安装不保证可见。真肘膝、Java ACTION绝对校准、Slim／自定义骨架、可见动作及骑车仍有差异。见[当前玩家动作范围](docs/PARITY.md#玩家動作的來源與骨架)。
- 小电驴使用 Bedrock 原生载具物理；跳跃键／控制面板触发喇叭。灯面发光，但不能动态照亮周围地形。
- 炉灶保留 9 条原版烟熏配方，安装有效物品后再接入烟火的烤鸡翅、烤番薯；其他供应商可通过明确的烟熏配方接口接入。三路共用 200 tick，支持实际产量及成品堵塞。调酒、烤串、炒锅仍用原设备；食品目录不会自动变成炉灶配方。详见 [配方对照与供应契约](docs/STOVE-RECIPES.md)。
- Jade 设备信息改用 addon action bar，并非 Jade 本身。SDM Currency、Touhou Little Maid、Aeronautics／Sable 等 API 未直接移植，可配置已有的 Bedrock 货币物品及登记特殊食物。
- 个人进度是包内的清单与通知，不会解锁 Xbox 官方成就或额外给金币。过期外送包必须由原生食用动作吃完才解锁，且不补饱食度。
- 增加基础设备合成和商店获取路径，避免生存开局拿不到第一批设备；商店价格属于首版适配值。

## 菜单与食品变体（尚未发布的源码修复）

已经公开 `senluo.public.food.v1` 的食品使用 `nativeVariant`，以物品 ID＋变体创建菜品与订单；备料仅消耗匹配变体，缺料会提示所缺变体。热度、品质与调味不会成为新菜或报酬倍率。未公开变体的旧菜单／订单继续只按 ID 匹配。同一 ID 的通用菜与指定变体不能同时加入菜单；须先移除通用菜再添加指定变体。

菜名与营养在登记时固定；修改虚拟营养设置不再偷偷改写已有菜品和订单，须移除并重新登记。背包选择菜品后还会重新检查原物品，避免表单开启期间物品移走或被替换却登记成功。

食品目录已接入烟火 59 种、酒馆 4 种葡萄及世界名酒 4 种甜点；秘制串、串盘、花椒按 Java 基础营养各计 1。饮品另有酒馆 45 款、世界名酒 27 款，涵盖 282 个实际 ID；以明示的 Bedrock 扩展允许营养 0 的饮品进入菜单和订单，沿用既有基础服务报酬。森罗共 139 种菜品／425 个实际 ID，直接持有即可登记，呈现／品质别名随订单保存，旧菜单和订单保留原匹配规则。其他 Addon 可用[食品供应接口](docs/FOOD-PROVIDERS.md)自动登记；V1 本身不提供营养。完整 ID、花椒手持食用缺口及获取限制见[食品目录](docs/FOOD-CATALOG.md)，执行结果见[本轮验证](docs/validation/UNRELEASED-food-catalog.md)。

## 个人进度与设备信息

通过指南“个人进度”或有权限管理的打单机打开入口。11 条清单可查看条件；可返回清单，关闭后回游戏。成功交单的结算（含小费与惊喜加赏）记在**实际交餐玩家**名下，跨店累计；消费或拾取金币不改变这个累计值。

金牌餐厅根据原版源码逐维度判定：同一玩家在**同一维度**拥有至少 4 家仍放置的餐厅，其中一家营业额并列或独占维度第一。暂停营业或区块未加载的餐厅仍计数，确认已拆除的不计数。零营业额并列有效；跨维度的 2＋2 家不等于 4 家。参见[PROGRESSION.md](docs/PROGRESSION.md)。

看向 6 格内有权限使用的设备，HUD 显示真实盘数、包装物资、洗碗阶段、冰箱上下层占用格数或炉灶进度。冰箱上层 27 格、下层 54 格。观察不会创建库存或移动物品。第一行优先手洗进度；第二行保留主手有效外送票据／包裹导航。手洗需双手空；结束后重新拿外送物品即可恢复导航。

## 管理员设置与兼容

只有创造模式玩家、带 `otc_admin` 标签的玩家或服务端命令可以更改全局设置。控制台没有玩家时不能发放个人测试套组。

```mcfunction
/tag @s add otc_admin
/scriptevent ordertocook:kit
/scriptevent ordertocook:refresh
```

`kit` 为测试套组，`refresh` 是 24 格内打单机的测试刷新，**正常生存开店不需要**。

已经接入目录或供应接口的食品会自动识别。管理员若需覆盖其他已安装食品的明确营养值，仍可使用原命令：

```mcfunction
/scriptevent ordertocook:food {"typeId":"example:your_dish","nutrition":12,"label":"你的料理"}
/scriptevent ordertocook:config {"currencyItem":"minecraft:emerald"}
/scriptevent ordertocook:config {"currencyItem":""}
```

`example:your_dish` 是示例 ID，必须换成实际已安装物品。空货币 ID 恢复默认 oTc 币。自定义货币每件视作 1 单位；切换仅影响之后的付款，不自动兑换已持有的旧币。

可以测试其他刷新周期／升级门槛，例如：

```mcfunction
/scriptevent ordertocook:config {"refreshSeconds":30,"upgradeNutrition":[0,25,40,60,80,100,120,140,159]}
```

**示例会偏离原版平衡。** 原版升级门槛是 `[0,40,80,120,160,200,300,400,600]`，刷新 600 秒。烹饪扩展入口见 `SMOKING_RECIPES`、`FUEL_TICKS` 及 [RUNTIME_ADAPTATIONS.md](docs/RUNTIME_ADAPTATIONS.md)。

## 开发与复现

需要 Node.js 22+、Python 3.12+。生成资源纳入版本控制；正常构建不需要重新下载原作或安装美术工具。

```sh
npm ci
npm run verify
python tools/check_compliance.py
```

`dist/` 包含 `.mcaddon`、独立 `.mcpack`、`SHA256SUMS.txt` 和 runtime 指纹。若修改原始模型或转换器：

```sh
python -m pip install Pillow==12.3.0
python tools/convert_assets.py
npm run verify
```

转换器默认使用 `upstream/reference/` 固定来源子集，也可指定 `--source /path/to/full/OrdertoCook`。固定基线见 [upstream/source.lock.json](upstream/source.lock.json)。

原生服务器测试须从 [Minecraft 官网](https://www.minecraft.net/en-us/download/server/bedrock) 自行获取 Linux BDS，解压到**没有其他世界的独立临时测试目录**：

```sh
python tools/bedrock_smoke.py --server-dir /path/to/disposable-bds --mode initial
python tools/bedrock_smoke.py --server-dir /path/to/disposable-bds --mode reload
```

探针不在正式安装包中启用，仅由测试工具注入一次性副本。
